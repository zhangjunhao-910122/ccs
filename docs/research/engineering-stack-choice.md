## 0. 为什么是空骨架

§8 的十二项选型（后端、前端、解释器、依赖管理、检查、类型、密钥、数据库、OpenAPI、部署）已经在票 #32 内拍板并写入规格，依据的**采集**被有意推迟：本项目的真实数据由用户后期录入，agent 侧不去抓取一手来源，也不凭记忆写版本号。

推迟采集不影响下游开工，理由有三条：

1. §8 的每项都写了「唯一权威的锁定机制」（锁文件、配置文件、白名单），**版本号本身不是决策输入**——锁文件才是事实来源，改版本由锁文件驱动，不由文档驱动。
2. 地图 #22 的硬约束是「未核验数值不进自动判定」；未采集的一手数据按「待录入」处理，比凭印象写死的版本号更安全。
3. 检查器 `docs/spec/engineering/reference_structure.py` 的 S9 白名单只校验「是否在 §8 登记过」，不校验版本号，因此本文件保持骨架不影响 S1–S10 的任何一条。

录入完成前，§8 不写版本号；录入完成后，按 §0.3 回填 SPEC。

## 0.1 录入规则

| 规则 | 内容 |
| --- | --- |
| R1 只采一手来源 | 官方文档站、官方发布说明、官方仓库的 LICENSE 文件、PyPI 与 npm 官方包页、PEP 官方状态页。不用博客、教程、Stack Overflow、聚合站。 |
| R2 找不到就写「未核实」 | 官方来源查不到明确说明时，写「官方文档未见明确说明」，不得用经验补齐。 |
| R3 版本号纪律 | 版本号只在 R1 来源能核实时写出；核实不到写「未核实」。**严禁凭印象填版本号。** |
| R4 许可证只写 SPDX 标识 | 写 SPDX 标识并给出官方 LICENSE 文件链接；标识取不到写「待录入」。 |
| R5 一项一来源 | 每个结论后面跟它自己的来源链接；多个来源时标注哪个是一手、哪个是二手。 |
| R6 冲突不上报则不选 | 若录入中发现某项选型与 §5 硬约束存在致命冲突，**不自行改选型**，在 §4 记录冲突证据并交维护者裁定。 |

## 0.2 每项的待录字段

每个登记项固定六个字段，录入时逐字段补齐：

1. **官方来源 URL** —— R1 来源，直接可打开。
2. **官方要点** —— 一到两句事实陈述（官方文档怎么说的），不写推测。
3. **许可证（SPDX）** —— 标识 + 官方 LICENSE 链接。
4. **版本策略** —— 锁文件机制、版本下限依据、官方维护状态与生命周期依据。
5. **离线交付方式** —— 官方文档是否支持无网环境下的安装/打包/分发；查不到写「官方文档未见明确说明」。
6. **与五条硬约束的冲突判定** —— 逐条写「无冲突 / 有冲突（说明）」或「待录入」。

### 1.1 判定用到的五条硬约束

录入时逐条对照下列五条，任何一条判「有冲突」都要在 §4 留痕：

- **C1 完全离线可装可跑** —— 企业受控域内网，无公网包源。
- **C2 单进程单库** —— 并发规模为 5–10 名交易员 + 1–2 名主管/风控。
- **C3 SQLite → PostgreSQL 双阶段** —— 类型与 SQL 只用两者交集（见 #25 存储层规格）。
- **C4 审计日志只追加、不可篡改** —— 见 #29 AU18 事件结构与 §7.1。
- **C5 类型边界靠静态检查兑现** —— Suggestion 与 NumericResult 不可互换，由 S7 与 mypy 双重保障。
