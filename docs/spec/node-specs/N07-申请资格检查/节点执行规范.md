## 2. 启动条件与输入清单

### 2.1 启动条件

- 前置节点：N03；前项须已具备交接条件或已完成，且其交接三件套（产物、契约摘要、未决事项清单）齐备。
- 依据状态：适用依据在依据库中的状态为 `current`；`superseded` 转「等待补件」，`unverifiable` 的条款只能落 `insufficient` 且本节点不得推进到「已具交接条件」，未登记按 `BASIS_NOT_REGISTERED` 处理转「等待补件」。
- 闸口：本节点不单独承载人工闸口；闸口 G1~G6 的落点见《成果与完成交接规范》与节点索引表。闸口一旦在其他节点未放行，本节点的交接条件同样不得满足。
- 节点状态：自「待执行」进入「进行中」；缺件即停，停在触发检查点转对应等待态并产出双成果标未完成。

### 2.2 输入清单

| 输入项 | 来源 | 必需性 | 缺失处置 |
|---|---|---|---|
| N03 缺口台账与材料清单 | 上游节点产出 | 必需 | 缺件→等待补件 |
| 认证申请书及受审核方体系概况 | 委托人提交 | 必需 | 缺件→等待补件 |
| 申请范围与场所清单 | 委托人提交 | 必需 | 缺件→等待补件 |
| 体系建立与运行的证据 | 委托人提交 | 必需 | 缺件→等待补件 |
| 拟申请的认证依据条款清单 | 审核员整理 | 必需 | 缺件→等待补件 |

### 2.3 本节点可用的判定与成果状态

- 节点状态（11 态）：待执行 / 进行中 / 等待补件 / 整改中 / 等待现场核实 / 等待人员确认 / 等待机构结果 / 已具交接条件 / 已完成 / 不适用 / 终止。
- 判定四态：conform / nonconform / insufficient / na；事实四态：user_stated / material_supported / verified / conflict；成果四态：waiting / review / final / terminated。
- 原因码：BASIS_MISSING、BASIS_UNVERIFIABLE、BASIS_SUPERSEDED、APPLICABILITY_UNKNOWN、NA_WITHOUT_BASIS、EVIDENCE_MISSING、EVIDENCE_CONFLICT、EVIDENCE_UNREADABLE、SAMPLING_INSUFFICIENT、CLAUSE_NOT_IN_TREE、GAP_CONFIRMED、REPORT_ITEM_MISSING、DECISION_BLOCKED_OVERDUE。

## 3. 节点内执行顺序

1. 登记任务标识与节点编号，建立本节点成果目录与索引行。
2. 按 CNCA 5.1 与 5.2 逐条列出认证申请与申请评审的受理条件，形成条件检查表。
3. 逐条打勾并登记每条条件的证据来源与锚点。
4. 把不符合受理条件的情形登记为不予受理候选，写明条款依据。
5. 对无法确认的条目保留 pending，登记责任方与期望回复。
6. 由具名责任人给出资格结论（受理、退回补件、不予受理）。
7. 输出双成果并按类型N1 的口径写结论。

节点内不并行执行（步骤 1→2→… 顺序推进）；任一必需检查缺件、冲突、未核验或缺必要确认时，停在该检查点转对应等待态，不得进入下一节点。

| 检查对象 | 本项所需证据 | 执行动作 | 对应规则 |

## 5. 阻塞、补件与退回执行

### 5.1 阻塞态与阻塞条件

| 阻塞态 | 触发条件 | 本节点内的处理 |
|---|---|---|
| 等待补件 | 必需输入缺件、依据快照 `superseded` 或未登记、文件不可读 | 停在触发检查点，登记缺件与责任角色，产出双成果并标未完成 |
| 整改中 | 已开具的不符合项处于 submitted 且需受审核方实施整改 | 登记整改跟踪状态，不代替受审核方实施 |
| 等待现场核实 | 现场事实需二次取证或需受审核方现场确认 | 登记待核实事项与所需证据 |
| 等待人员确认 | 冲突未解、适用性未确认、需具名责任人确认 | 登记冲突两侧证据与确认人，不得择一采信 |
| 等待机构结果 | 需认证机构或外部机构出具结果 | 登记等待对象与期望回复 |

### 5.2 补充材料后的复核

1. 登记版本：文件名、路径、sha256、取得时间、来源人。
2. 在当前项按原接受条件复核，不得改标「不适用」。
3. 写明改变了哪条判定及其依据。
4. 未解决的保持原状态，不得推进到下一节点。

### 5.3 退回执行

退回记录字段：`rollback_from`、`rollback_to`、`reason`、`evidence`、`affected_downstream`、`disposition`。恢复后节点回到「进行中」，须重新满足全部交接前置条件方可再次转「已具交接条件」。

## 6. 节点异常专门要求

- 任一受理条件无法确认时保持 pending，转「等待补件」或「等待人员确认」，不得直接给结论。
- 结论只能由人给出；工具只提供逐条打勾结果与依据摘要。
- 发现申请信息或文件不实时按 CNCA 5.6.2.4 的精神登记冲突并转「等待人员确认」。
- 本节点结论仅表示就绪度，不得写成符合性结论。

## 7. 照片取证边界

以下 4 类事实不可由照片取证，缺失时直接落 `insufficient`，不得以照片替代：

| 类别 | 不可由照片取证的说明 |
|---|---|
| 文件内容完整性 | 受控版本、审批记录、修订痕迹只能由书面文件与原件核验核对，不得据照片认定。 |
| 访谈 | 人员理解、认知与授权只能由访谈记录核验，不得据照片推断访谈内容。 |
| 时间序列类 | 10.2 纠正措施有效性与 9.3 管理评审有效性属时间序列事实，不得据照片认定有效性。 |
| 数据真实性与完整性 | 记录是否真实反映实际过程只能由原始记录与交叉核对核验，不得据照片认定。 |

审核点库 `photo_evidence` 字段取值 `allowed` / `conditional` / `not_applicable`；取 `not_applicable` 的审核点必须走书面证据或访谈记录。视觉桥（modlens）不可用时，照片锚点的 `fact_state` 不高于 `user_stated`，并生成 E 组 `pending_check` 待办。image 锚点必须 `visible_state_only=true`。

## 9. 数值依赖与引用口径

本节点不产生独立数值结论。上下文中出现的人日、比例、间隔、抽样数量与验证时限，一律按 S3 §7 的口径写「引用 #21 计算结果（tools/calculate.py、tools/calendar_ratio.py、tools/params.yaml）」或「待核」，不得写死数字。

## 10. 本节点结束

- 本节点产出的双成果与逐项完成核查表见《N07 成果与完成交接规范》。
- 转「已具交接条件」的机器可判定前置条件：逐项完成核查表全部「已执行」且有通过证据；全部规则均已判定无未判定检查项；无未结等待态（可作为已登记未决事项显式列出）；若产出判定则锚点表已存在且每个结论可回指锚点与依据，依据 unverifiable 只能落 insufficient；数值类结论均引自 #21 计算结果且 `source_ref` 与核验状态齐备。
- 已具交接条件 → 已完成 为终态迁移；已完成、不适用、终止为终态，不得回退。
