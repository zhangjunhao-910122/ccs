# 输出格式规格：成果形态、文件结构与占位符纪律（S4）

> 对应 GitHub Issue #10（规格 S4）。上游：#9（判定与证据锚点，`docs/spec/verdict-anchor-rules.md`）、#2（审核点库 schema 与画像注册表）、#4（流程与状态机）；下游：#12、#15、#11、#6、#19（机构表单族原件与占位化）、#21（人日／抽样／期限计算）。
> 依据：CNCA-QMS-01:2025 / EMS-01:2026 / OHSMS-01:2026 的一手核验见 `docs/research/multi-system-audit-research.md`；流程骨架见 `docs/research/process-flow-research.md`；审核点字段见 `audit-point-library/registry.yaml` 与 `profiles/quality/gbt19001-2016.yaml`。
> 本文件只定义**成果的形态、字段、命名与校验**；判定语义一律以 #9 为准。

## 0. 范围、枚举口径与产物链路

### 0.1 边界

本文件定：产物种类与格式、列定义与章节结构、成果四态与命名规则、目录结构与覆盖纪律、占位符字典与校验规则、签署边界、可自动检查的交付判据、机构表单族清单与占位化要求。
本文件**不定**：判定语义与算法（#9）、流程节点与状态机（#4）、依据库快照核验（#20）、人日／抽样／期限数值（#21）、机构表单原件与版式（#19）。

### 0.2 枚举口径（唯一来源，不得另造）

全部枚举值逐字取自 `docs/spec/verdict-anchor-rules.md` §1、§2.2、§3.2、§4、§13.1，实现时从同一模块导入。

| 组 | 名称 | 取值 | 本文件用途 |
|---|---|---|---|
| A | 判定四态 | `conform` / `nonconform` / `insufficient` / `na` | 审查表「判定结论」、对照表「结论」、报告「审核发现」 |
| B | 事实标记四态 | `user_stated` / `material_supported` / `verified` / `conflict` | 锚点表 `fact_state` |
| C | 辅助判断 | A 四态 ∪ `pending` | 人工暂定结论字段（可选） |
| D | 成果态 | `waiting` / `review` / `final` / `terminated` | 文件后缀、流转、目录索引（§1） |
| E | 问题七分类 | `missing` / `unreadable` / `pending_check` / `conflict` / `suspected_nc` / `formal_nc` / `suggestion` | 待处理事项、报告「改进机会」 |

**原因码全集**（`reason_codes` 只能取这些值，照抄 #9 §13.1）：
`BASIS_MISSING`、`BASIS_UNVERIFIABLE`、`BASIS_SUPERSEDED`、`APPLICABILITY_UNKNOWN`、`NA_WITHOUT_BASIS`、`EVIDENCE_MISSING`、`EVIDENCE_CONFLICT`、`EVIDENCE_UNREADABLE`、`SAMPLING_INSUFFICIENT`、`CLAUSE_NOT_IN_TREE`、`GAP_CONFIRMED`、`REPORT_ITEM_MISSING`、`DECISION_BLOCKED_OVERDUE`。

**红线承接**：判定不可自由书写（结论句必须能追到判定记录）；「不适用不是垃圾桶」；认证决定、严重不符合分级、报告第 19 项由人作出，工具不代作。

### 0.3 产物生成链路

```
依据库快照(#20) ─核验(退出码3→insufficient/BASIS_UNVERIFIABLE)─┐
审核点库画像(#2) ─────────────────────────────────────────────────┤
                                                                       ↓
anchors ─→ judge()(#9 §3.3) ─→ judgements(+sampling/basis/applicability)
              ├→ nonconformities(#9 §8，category 由人填)
              └→ 过程底稿.json（唯一事实源）→ report_refs(19项)
                                        ↓ 投影
    审查表.xlsx ｜ 条款-证据对照表.xlsx ｜ 审核报告.docx ｜ 预览.md
```

**纪律**：四份派生产物**全部由同一份 JSON 底稿投影生成**；不允许先写正文再补锚点（#9 §2.3）。生成器是无副作用的纯投影，同底稿两次生成字节级一致。

## 1. 成果四态（D 组）与状态维度映射

### 1.1 四态与状态维度映射表

| 状态维度取值 | 成果态 | 中文名 | 文件名后缀 | 进入条件 | 退出条件 |
|---|---|---|---|---|---|
| 编制中 | `waiting` | 等待版 | `-waiting` | 节点启动即建，判定未复核 | 提交复核 → `review`；终止 → `terminated` |
| 待确认稿 | `review` | 复核版 | `-review` | 内容齐备、已提交复核、未签署 | 通过并签署 → `final`；退回 → 新建 `waiting`；终止 → `terminated` |
| 退回修订 | `waiting`（由 `review` 退回） | 等待版 | `-waiting` | 复核未通过 | 产生新版本号后重提；被退回的 `-review` 版保留并标 `superseded_by` |
| 已确认提交版 | `final` | 完成版 | `-final` | 复核通过 + 签署完成 + §12 判据全通过 | 终态；出新版时旧版标「被新版替代」 |
| 被新版替代 | 不改原文件状态，仅作标记 | — | （保留原后缀） | 索引中存在更新版本 | 旧文件**不删不改**，仅在索引置 `superseded_by` |
| （终止事件） | `terminated` | 终止版 | `-terminated` | 审核终止或节点作废（CNCA 5.11.5） | 终态；终止原因与已开展工作情况形成报告提交委托人 |

> 「被新版替代」是**版本关系**而非第五个成果态：状态维度 5 个取值，成果态只有 4 个（D 组枚举不得扩充），按上表对齐。

### 1.2 允许的流转

| 从 | 到 | 触发条件 |
|---|---|---|
| `waiting` | `review` | 提交复核；前自检：条款判定齐全、19 项无缺、不符合项 `category` 已填或明确待填 |
| `waiting` | `terminated` | 任务终止 |
| `review` | `waiting` | 复核退回修订（新版本号） |
| `review` | `final` | 复核通过 + 签署完成 + §12 判据全通过 |
| `review` | `terminated` | 任务终止 |
| `final` | — | 终态，**不得**再改写 |

**禁止流转**：`waiting` → `final`（跳过复核）；`final` → 其他态（须开新版本）；`review` 覆盖同名文件（须换版本号）。

## 2. 产物清单、命名规则与目录结构

### 2.1 文件级产物清单（五件，四类格式）

| # | 基名（固定） | 格式 | 类别 | 承载内容 | 双成果归属 |
|---|---|---|---|---|---|
| 1 | `审查表.xlsx` | XLSX | 正式文件 | 逐审核点判定与整改台账 | 正式文件 |
| 2 | `条款-证据对照表.xlsx` | XLSX | 正式文件 | 逐条款证据溯源对照 | 正式文件 |
| 3 | `审核报告.docx` | DOCX | 正式文件 | 审核报告正文（6 章 + 19 项映射） | 正式文件 |
| 4 | `过程底稿.json` | JSON | 正式文件 | 锚点表 + 判定记录 + 不符合项 + 报告引用映射（唯一事实源） | 正式文件 |
| 5 | `预览.md` | Markdown | 简报 | 沟通交接用一页简报（§8） | 简报 |

### 2.2 命名规则

```
<任务标识>_<节点编号>_<成果名称>_<版本>.<扩展名>
```

| 段 | 取值 | 规则 |
|---|---|---|
| 任务标识 | 如 `TASK-2026-QMS-A` | 同一委托、同一审核轮次的唯一标识；不得含机构名称 |
| 节点编号 | 如 `N12` | 取自 #4 状态机节点编号 |
| 成果名称 | 成果基名 + 状态后缀 | 基名取 §2.1；后缀见下表 |
| 版本 | `v1`、`v2`…… | 节点内单调递增；跨态重新计数，**不复用旧版本号** |

**状态后缀**（与 D 组枚举一一对应，便于机器从文件名判定状态）：

| 成果态 | 后缀 | 完整文件名示例 |
|---|---|---|
| `waiting` | `-waiting` | `TASK-2026-QMS-A_N12_审查表-waiting_v1.xlsx` |
| `review` | `-review` | `TASK-2026-QMS-A_N12_审查表-review_v2.xlsx` |
| `final` | `-final` | `TASK-2026-QMS-A_N12_审查表-final_v3.xlsx` |
| `terminated` | `-terminated` | `TASK-2026-QMS-A_N12_审查表-terminated_v1.xlsx` |

其余四件同规则替换基名；`过程底稿.json` 与 `预览.md` 用同一组后缀与版本号，保证「同一版五件配套」。

### 2.3 目录结构（原件与派生稿分开）

```
<任务根>/
  00_原始材料/            # 原件：只读，工具不得修改、不得覆盖
    依据库快照/  委托人提交/  现场取证/
  01_工作稿/              # 中间态、可变，不作为交付物
  02_成果/                # 正式文件（四件），按节点分目录
    N12_第二阶段审核/
      TASK-2026-QMS-A_N12_{审查表|条款-证据对照表|审核报告|过程底稿}-final_v3.{xlsx|docx|json}
  03_简报/                # 简报（一件），用于沟通交接
    N12_第二阶段审核/TASK-2026-QMS-A_N12_预览-review_v3.md
  04_索引/                # index.json：版本、状态、哈希、替代关系
```

**硬规则**：① `00_原始材料/` 下文件**只读**，清洗、占位化、日期替换只在复制出的副本上做（外部门禁「模板原件一个字节都不动」原则，见 `docs/research/external-package-and-uicc-review.md` §2.7）；② 派生稿**不得**回写原件目录；③ `01_工作稿/` 不得直接交付，须经 §2.1 的五件投影。

### 2.4 版本、覆盖与索引

| 规则 | 内容 |
|---|---|
| 不静默覆盖 | 目标文件名已存在时**拒绝写入并报错**，不得覆盖、不得追加、不得就地更新 |
| 旧成果保留 | 出新版时旧文件原地保留；索引中旧行置 `superseded_by: <新文件名>` |
| 内容不可变 | 已写入文件不再改写；任何修改都产生新版本号 |
| 索引字段 | `file_name`、`artifact_base`、`node_id`、`artifact_state`、`version`、`sha256`、`created_at`、`superseded_by`、`review_history`、`signed_by` |
| 配套校验 | 同节点同一版本号的五件文件必须 `sha256` 成套出现；缺件即该版不完整，不得标 `final` |

## 3. 四种产物形态（Q12 决策）

Q12 决策：成果按**四类格式**落地，XLSX 承载两张表，共五件文件。

| # | 产物 | 格式 | 为什么是这个格式 | 谁看 |
|---|---|---|---|---|
| 1 | 审查表 | XLSX | 逐审核点判定，需排序筛选、多人分工填写与回填 | 审核组 |
| 2 | 条款-证据对照表 | XLSX | 一条款多锚点，需扁平多行，便于与抽样记录、报告章节对照 | 审核组长、复核人 |
| 3 | 审核报告正文 | DOCX | 需版式、章节层级、签署栏与可打印性；对外提交物 | 委托人、认证决定人员 |
| 4 | 过程底稿 | JSON | 唯一事实源，需机器可读、可复现、可 diff、可被下游消费 | 工具链、复核人 |
| 5 | 预览 | Markdown | 一页看完本节点状态与待办；不进正式交付包 | 委托方对接人、组长 |

**投影关系**：审查表与对照表的每一行、报告的每个引用、简报的每条待办，都必须能在 `过程底稿.json` 中找到对应字段；反向禁止——先写报告再补锚点。

## 4. XLSX 审查表列定义

### 4.1 列定义表

| # | 列名 | 类型 | 取值域 | 来源字段 | 必填 | 由谁填 |
|---|---|---|---|---|---|---|
| 1 | 审核点ID | 文本 | `point_key`，形如 `8.5.2#1` | `judgements[].point_key` | 必填 | 工具生成（人工改动即脱离审核点库） |
| 2 | 条款号 | 文本 | `clause_no`，形如 `8.5.2` | `judgements[].clause_no` | 必填 | 工具生成 |
| 3 | 条款标题 | 文本 | 画像条款标题；`verification_status` 非 `toc_verified` 时附「（中文标题待核定）」 | 画像 `clauses[].title` | 必填 | 工具生成 |
| 4 | 审核问题 | 长文本 | 审核点库提问原文 | 画像 `points[].audit_question` | 必填 | 工具生成 |
| 5 | 判定结论 | 枚举 | `conform` / `nonconform` / `insufficient` / `na` | `judgements[].verdict` | 必填 | 工具出建议，人复核确认（记第 10 列） |
| 6 | 证据锚点 | 文本（逗号分隔） | `A-0001, A-0012`；无则写 `-` | `judgements[].anchors` | 必填（无锚点写 `-`） | 工具生成 |
| 7 | 判定依据 | 长文本 | 模板拼装：适用性 + 依据状态 + 事实状态 + 原因码 | `expression`、`reason_codes`、`applicability`、`basis` | 必填 | 工具生成（不得自由撰写） |
| 8 | 不符合类别 | 枚举 | 空 / 严重 / 轻微 | `nonconformities[].category` | 条件必填：`verdict=nonconform` 时 | **人填**（工具不得预填，不得写「建议：严重」） |
| 9 | 整改要求 | 长文本 | 原因分析要求 + 纠正措施要求 + 完成时限 | `remediation_required`、`due_date` | 条件必填：`verdict=nonconform` 时 | 人填（时限**引用 #21 计算结果**） |
| 10 | 审核员确认 | 枚举 | 空 / 已确认 / 退回 | `judgements[].reviewed_by` + `reviewed_at` | 条件必填：已复核时 | 人填（工具只置空） |

### 4.2 填写纪律

1. **一审核点一行**，行序按 `point_key` 升序；同一条款的多个审核点不合并。第 5 列在 `waiting` 版即为建议值，但第 10 列必须留空，未复核不得出 `final`。
3. 第 6 列只列本行引用的锚点；引用未 `confirmed` 锚点违反 #9 §2.3 硬规则一，生成器应拒绝出稿。
4. 第 8、9 列在 `waiting`／`review` 版一律留空，工具**不得**预填任何不符合分级（#9 §8.3.1、V8）。
5. 第 7 列必须是模板拼装结果，模板缺字段时输出「描述不可生成」而非自由补写（#9 §3.3）；`insufficient` 行至少一个原因码；`na` 行须写明适用性依据与 `applicability.basis_anchor`（#9 V4）。

## 5. XLSX 条款-证据对照表列定义

### 5.1 列定义表

| # | 列名 | 类型 | 取值域 | 来源字段 | 必填 | 由谁填 |
|---|---|---|---|---|---|---|
| 1 | 条款号 | 文本 | `clause_no` | `judgements[].clause_no` | 必填 | 工具生成 |
| 2 | 条款标题 | 文本 | 画像条款标题（同 §4.1「待核定」规则） | 画像 `clauses[].title` | 必填 | 工具生成 |
| 3 | 结论 | 枚举 | `conform` / `nonconform` / `insufficient` / `na` | `judgements[].verdict` | 必填 | 工具出建议，人复核 |
| 4 | 锚点ID | 文本 | `A-0001` | `anchors[].anchor_id` | 必填（确无锚点写 `-`） | 工具生成 |
| 5 | 锚点定位 | 文本 | file：`{kind: page｜section｜table_row｜cell｜paragraph｜timestamp, value}`；image：`{kind: bbox｜region_desc｜tag, value}`；并附 `source_ref` | `anchors[].locator`、`source_ref` | 必填 | 工具生成 |
| 6 | 摘要 | 长文本 | 观察事实，**只写看到了什么** | `anchors[].evidence.observed` | 必填 | 工具生成（不得含推断） |
| 7 | 缺口说明 | 长文本 | `conform` → `无`；`nonconform` → 差距描述；`insufficient` → 缺失必核项 + 原因码；`na` → 适用性依据摘要 | `reason_codes` + `applicability` | 必填 | 工具生成 |

### 5.2 填写纪律

1. **一条条款多锚点 → 多行**，结论列每行重复，条款顺序按条款树顺序；`insufficient` 条款必须出现，即使无锚点（第 4 列写 `-`），保证「未覆盖」可见。
2. 第 5 列必须指向**具体位置**，禁止只写文件名或整页引用；整页引用须写明所引段落范围（#9 §2.2 硬规则 5）。
3. 第 6 列「看到了什么」、第 7 列「差在哪」不得互相顶替；对照表**不含**结论性新语句，结论一律由第 3 列枚举承担（#9 §11.3）。

## 6. DOCX 审核报告正文结构

### 6.1 章节骨架

```
封面页：报告编号、审核类型、成果态、版本、编制/复核/签署栏
§1 审核依据
   1.1 审核准则与认证机构      1.2 审核类型与审核目的
   1.3 结合/联合/一体化审核说明  1.4 审核组构成（组长、审核员、同行人员）
§2 审核范围
   2.1 受审核的组织、职能单元或过程   2.2 审核时间与抽样（总体、方法、限制）
   2.3 偏离审核计划的情况及理由；影响审核方案的重要事项
   2.4 审核活动实施日期、地点与场所性质（现场/非现场、永久/临时）
§3 受审核方信息
   3.1 委托人名称、地址及其代表   3.2 行政监管部门抽查不合格情况及整改有效性
   3.3 上次审核后影响体系的重大变更  3.4 证书与标志使用控制
   3.5 以前不符合项的纠正措施有效性验证
§4 审核发现
   4.1 符合项（按条款）  4.2 不符合项（按 #9 §8 模板）  4.3 改进机会（E 组 suggestion）
§5 结论与建议
   5.1 审核目的达成情况的确认  5.2 已识别出的未解决问题
   5.3 抽样过程的免责声明（机器生成固定句式）
   5.4 审核组推荐意见与认证范围适宜性结论（人写）
§6 附件索引
   6.1 附件清单（附件号、名称、对应底稿位置、是否需签署）
   6.2 证据留存说明（锚点表与报告一同留存，CNCA 5.11.4）
```

### 6.2 CNCA 5.11.3 十九项 → 正文章节映射表

逐项覆盖 CNCA-QMS-01:2025（EMS／OHSMS 同构）5.11.3 全部 19 项。**「不适用处理」栏为强制**：凡标注「适用时」的项，即使本次不适用，也必须在报告对应章节写明不适用理由，不得留空、不得直接省略该节。

| # | 5.11.3 要求内容 | 落位章节 | 数据来源（底稿字段） | 不适用处理（强制） |

## 7. JSON 过程底稿结构

### 7.1 顶层与三个子结构

```json
{
  "schema_version": 1,
  "artifact": {"task_id": "TASK-2026-QMS-A", "node_id": "N12",
    "artifact_base": "过程底稿", "artifact_state": "review", "version": "v3",
    "generated_at": "<时间戳>", "basis_snapshots": [{"source_ref": "...", "status": "current"}]},
  "anchors": [], "judgements": [], "nonconformities": [], "report_refs": []
}
```

### 7.2 子结构一：锚点表 `anchors[]`

字段名照抄 #9 §2.2：`anchor_id`（`A-` + 4 位序号，全局单调递增、不复用不回收）、`type`（`file｜image`）、`source_ref`、`locator`（file：`{kind: page｜section｜table_row｜cell｜paragraph｜timestamp, value}`；image：`{kind: bbox｜region_desc｜tag, value}`）、`fingerprint`（`{hash}` 或 `{size, mtime}`，file 锚点必填）、`fact_state`（B 组枚举）、`confirmation`（`pending｜confirmed｜rejected`）、`confirmed_by`、`confirmed_at`、`visible_state_only`（image 锚点必为 `true`）、`evidence.observed`（只写看到了什么）。引用写作 `[A-0007]`，只有 `confirmed` 可进正文；必须指向具体位置，禁止只写文件名或整页引用；锚点表是唯一事实源，其余产物由其投影生成。

### 7.3 子结构二：判定记录 `judgements[]`

字段名照抄 #9 §3.4：

```json
{
  "clause_no": "8.5.2", "point_key": "8.5.2#1",
  "expression": "applicable && basis_current && verified_ok",
  "verdict": "conform", "reason_codes": [], "anchors": ["A-0011", "A-0012"],
  "applicability": {"state": "applicable", "reason": "<适用理由>", "process": "<过程>", "site": "<场所>", "basis_anchor": "A-0013"},
  "fact_states": ["verified", "material_supported"], "conflicts": [],
  "basis": {"source_ref": "...", "status": "current", "snapshot_sha256": "<sha256>"},
  "sampling": {"population": "<总体说明>", "method": "<抽样方法>", "limitation": "<覆盖限制>", "risk_basis": "<风险依据>", "selected": [], "excluded": []},
  "decided_by": "tool", "reviewed_by": null, "note": ""
}
```

取值域与规则：`expression` 与 #9 §3.2 映射表唯一对应；`verdict` 取 A 组枚举；`reason_codes` 取 §0.2 全集，`insufficient` 时至少一条；`applicability.state` 取 `applicable｜not_applicable｜unknown`，`na` 判定须有已 `confirmed` 的 `basis_anchor`；`basis.status` 取 `current｜superseded｜unverifiable`，非 `current` 不得下结论；`sampling` 中 `population/method/limitation` 缺一即未填；`decided_by` 取 `tool｜human`，`tool` 为工具建议，`reviewed_by` 有值才算复核。

### 7.4 子结构三：报告引用映射 `report_refs[]`

本表把 CNCA 5.11.3 的 19 项与报告章节、底稿记录绑定，是 §6.2 映射表的机器可读形态：

```json
{
  "report_item": 12, "section": "§4.1",
  "requirement_text": "与审核类型要求一致的审核发现、审核证据（或其引用）及审核结论……",
  "source": "judgements+anchors", "clause_nos": ["8.5.2"],
  "anchor_ids": ["A-0011", "A-0012"], "judgement_refs": ["8.5.2#1"],
  "not_applicable": false, "na_reason": null,
  "generated_by": "tool", "requires_human": false
}
```

取值域与规则：`report_item` 为 1～19 整数，须连续覆盖 1..19 无缺号；`section` 与 §6.1 骨架一致；`anchor_ids` 须都在 `anchors[]` 且 `confirmation=confirmed`；`not_applicable=true` 时 `na_reason` 不得为空；第 19 项 `generated_by=human`、`requires_human=true`。

### 7.5 序列化规则

1. 键顺序稳定（`schema_version` → `artifact` → `anchors` → `judgements` → `nonconformities` → `report_refs`），保证 JSON 往返稳定。
2. `nonconformities[]` 字段照抄 #9 §8.2（`id`、`clause_no`、`clause_text_ref`、`category`、`fact_statement`、`anchors`、`judgement_basis`、`remediation_required`、`due_date`、`status`、`confirmed_by`、`confirmed_at`）；工具产出时 `category` 必须为 `null`。
3. 底稿不含自由文本结论，所有句子可由模板字段拼装（#9 V12）。

### 9.2 残留校验

- 检出正则：`{{[^{}]*}}`（残留占位符），并统计裸花括号 `{` / `}`。
- 判据：五件交付物中**双花括号残留数 = 0**。
- 未填项处理：未填字段写「（待填）」／「（待签）」／「不适用（理由：…）」，**不得**保留 `{{...}}`。
- 例外登记：确需保留的占位符必须在底稿 `artifact.pending_placeholders[]` 登记，并在简报显式列出。
- 校验时机：每次生成后立即校验；不通过则**拒绝写出文件**并报错。

### 9.3 日期类替换的排除规则与正则

**事故背景**：外部包用「两位数字」匹配日期，把 `ISO 9001` 改成 `ISO 90{{时间}}15`（`docs/research/external-package-and-uicc-review.md` §2.7）。据此立硬规则。
**硬规则 R-D1**：年份匹配单元**必须是四位**，禁止用 `\d{2}` 或 `\d{1,2}` 作为年份匹配单元。

| 规则 | 保护对象 | 判据／正则 | 示例 |
|---|---|---|---|
| R-D1 | 一切年份 | 四位边界匹配：`(?<![0-9A-Za-z])(?:19|20)\d{2}(?![0-9])` | `ISO 9001` 中的 `9001` 不匹配 |
| R-D2 | 标准编号 | `(?<![0-9A-Za-z])(?:ISO(?:/IEC)?|GB/T|GB|CNCA(?:-[A-Z]{2,6})?|CNAS(?:-[A-Z]{2,6})?|IAF|JF)\s*[-–]?\s*\d+(?:[.\-:/]\d+)*` | `ISO 9001`、`GB/T 19001-2016`、`CNCA-QMS-01:2025` |
| R-D3 | 版本号后缀 | `\s*[:：]\s*(?:19|20)\d{2}`、`\s*[-–]\s*(?:19|20)\d{2}`，命中后并入保护 token | `ISO 9001:2015`、`GB/T 19001-2016` |
| R-D4 | 条款号 | 形如 `^\d+(\.\d+){1,3}$` 的上下文（5.11.3、8.5.2） | 不参与任何数字替换 |
| R-D5 | 附录与表号 | `附录\s*[A-Z]`、`表\s*[A-Z]\.\d+` | 附录 B、表 A.2 |
| R-D6 | 比例与系数 | `\d+%`、`0\.\d+X`（80%、30%、0.6X） | 不参与日期替换 |
| R-D7 | 人日／期限数值 | 由 #21 计算得出，一律写「引用 #21 计算结果」 | 不在文本替换链内 |
| R-D8 | 证书与表单编号 | 机构私有编号体系 | 不在文本替换链内 |

**替换流水线（顺序不可调换）**：① 掩码（R-D2/R-D3 抽保护 token 换哨兵）→ ② 结构化替换（按底稿字段逐键替换，不全文扫描）→ ③ 日期类替换（非保护上下文按 R-D1 匹配四位年份）→ ④ 还原哨兵 → ⑤ 不变式校验 → ⑥ 残留校验 → ⑦ 任一步失败即回滚报错，不写盘。
**不变式校验（必须）**：`list(re.findall(PROTECT_RE, before)) == list(re.findall(PROTECT_RE, after))`，不等即判定替换污染标准号，报错回滚。

### 9.4 机构私有信息隔离

机构表单号体系、认证机构名称、机构内部时限口径属机构私有信息，**不得**硬编码进产物模板或生成器；进入产物时一律走占位符字典。机构内部考核口径（如「多少天内交整改资料」）不是法定期限，不得写入报告或简报。

## 10. 签署边界

### 10.1 谁签、工具做什么

| 签署物 | 签署人 | 工具行为 |
|---|---|---|
| 首末次会议签到表 | 参会人本人 | 生成待签版本：签字栏留空并标注「（待签）」 |
| 声明类签字（公正性与保密性等） | 签署人本人 | 同上；**不代签、不生成签名图像、不仿制签章** |
| 审核报告签署（审核组长） | 审核组长 | 生成待签版本；未签署不得出 `final`（闸口 G5） |
| 报告第 19 项推荐意见与范围适宜性结论 | 审核组 | 只给「依据摘要」，正文写「（待填写）」 |
| 不符合项分级（严重／轻微） | 有权限的分级人 | `category` 留 `null`，工具不得预填、不得写「建议：严重」 |
| 认证决定 | 专职认证人员（非审核组成员） | 只提供 `decision_pack`，`decision_ready` 默认 `false` |

### 10.2 硬规则

① 工具**只生成待签版本**：签字栏、日期栏一律为空并标注「（待签）」；② 工具**不代签、不伪造签章、不生成签名或印章图像**，也不得放入图片形式的签名；③ 签署栏为空的产物只能是 `waiting` 或 `review`，出 `final` 前须校验签署字段已由真人填写（写入索引 `signed_by`）；④ 闸口 G5：缺第 19 项或缺审核组长签署 → 不出 `final` 版（#9 §12.3）；⑤ 闸口 G4：`category` 未填 → 不得进入报告「不符合项」栏终稿（仍可作 `review` 版待办）；⑥ 闸口 G6：认证决定由人作出，工具结论均为**建议**，含判定四态初值。

### 11.2 占位化与清洗要求（承接 #19）

① **原件不动**：替换只在复制出的副本上做，原件进 `00_原始材料/` 只读保存（§2.3）；② **机构私有信息一律占位化**：表单号、认证机构名称、机构内部时限全替换为 §9.1 字典条目，清单中**不出现**任何机构表单号；③ **替换后三道校验**：占位符残留为 0（§9.2）、标准号不变式成立（§9.3）、日期类字段落在允许清单内；④ **清洗日志留档**：记录原件哈希、清洗项、清洗后哈希，供 §12 的 O2 复现校验使用。

## 12. 交付判据（可自动检查的验收项）

| O6 | 标准号不变式 | 按 §9.3 保护 token 序列比对 | 替换前后序列逐项相等 |
