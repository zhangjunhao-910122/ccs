## §0 第一性原理、本票边界与不可协商前提

### 0.1 智能体究竟替审核员做什么

认证审核的本质是：**在有限时间内，用可追溯的证据，判断一组条款在特定组织、期间、场所上的符合性，并让结论经得起认证决定与申诉的复查**。

因此智能体的工作可以拆成三件不可再分的事：

1. **把证据变成可定位的锚点**（事实层）。谁能点回原文，谁才能复核。
2. **把锚点变成有依据的判定**（判断层）。每个结论必须能指回条款、依据、锚点、缺口。
3. **把判定变成可交接、可留痕、可被推翻的产物**（流程层）。不重写正文、不代作决定、不抹掉历史。

凡是不属于这三件事的（替审核员定级、替机构作认证决定、替企业回答管理层评审、现场代为观察事实），一律不做。这不是能力不足，是职责边界：越界的智能体产出的结论在认证法律关系中无效。

## §1 六维状态总表

### 1.1 维度与取值

状态分六维，每维独立取值，不允许用一维推另一维（尤其：任务「已完成」不等于节点「已完成」，更不等于判定「符合」）。

| 维 | 取值 | 归属 | 谁能改 |
|---|---|---|---|
| 任务 | 进行中 / 暂停 / 等待必要输入 / 已完成 / 已终止 | 一次审核任务 | 审核员 |
| 节点 | 待执行 / 进行中 / 等待补件 / 整改中 / 等待现场核实 / 等待人员确认 / 等待机构结果 / 已具交接条件 / 已完成 / 不适用 / 终止 | 单个节点 | 审核员 |
| 事实 | 用户陈述 / 材料支持 / 已核验 / 存在冲突 | 每条锚点 | 审核员确认后 |
| 辅助判断 | 有证据支持 / 证据不足 / 疑似不符合 / 来源冲突 / 不适用且理由已确认 / 待人员或机构确认 | 每个审核点 | 系统建议，人确认 |
| 成果 | 编制中 / 待确认稿 / 退回修订 / 已确认提交版 / 被新版替代 | 每份产物文件 | 审核员 |
| 正式结果 | 未取得 / 已取得待核 / 已核实 | 认证决定、验证结论等外部结果 | 出具方 |

「正式结果」维只用于记录**外部主体给出的结果**（认证决定、机构反馈、验证结论），不用于表达审核员的判定。

### 1.2 辅助判断 ↔ 判定四态的显式映射

《判定规格》§3 的判定四态是唯一结论口径：**符合 conform / 不符合 nonconform / 证据不足 insufficient / 不适用 na**。本票的「辅助判断」维是它的**未定态上游**，两者的映射必须唯一且单向：

| 辅助判断 | 可流向的判定四态 | 不可流向 | 约束 |
|---|---|---|---|
| 有证据支持 | conform 或 nonconform | na | 走《判定规格》§3 三段判定（applicability/basis/fact） |
| 证据不足 | insufficient | conform / nonconform / na | 缺件不得推断企业未实施 |
| 疑似不符合 | nonconform（须人工确认）；未确认时仍为 insufficient | conform | 确认前问题分类为 suspected_nc |
| 来源冲突 | 先 insufficient（分类 conflict）；冲突消解后方可定终值 | conform / nonconform | 不得按多数材料或有利版本定事实 |
| 不适用且理由已确认 | na | — | 必须同时具备依据；无依据走 NA_WITHOUT_BASIS，仍落 insufficient |
| 待人员或机构确认 | **只能先落 insufficient** | conform / nonconform / na（禁止直达） | pending 不得直接跳到终值 |

对应《判定规格》§13.1 的原因码：BASIS_MISSING、BASIS_UNVERIFIABLE、BASIS_SUPERSEDED、APPLICABILITY_UNKNOWN、NA_WITHOUT_BASIS、EVIDENCE_MISSING、EVIDENCE_CONFLICT、EVIDENCE_UNREADABLE、SAMPLING_INSUFFICIENT、CLAUSE_NOT_IN_TREE。

**禁止两套口径并存**：本表是「辅助判断」到「判定四态」的唯一映射表。任何工具、文档、界面出现第二张映射表即为缺陷。

### 1.3 事实维度 ↔ 事实标记四态

| 本票「事实」维 | 《判定规格》§2 的 fact_state |
|---|---|
| 用户陈述 | user_stated |
| 材料支持 | material_supported |
| 已核验 | verified |
| 存在冲突 | conflict |

事实维只描述证据本身的可信层级，**不描述符合与否**。「材料支持」不等于「符合」；「存在冲突」也不等于「不符合」。

### 1.4 成果维度 ↔ 文件级四态

《判定规格》与 #10 使用文件级四态标签，本票给出唯一映射：

| 成果维 | 文件级四态（D 组枚举值） | 文件名后缀（#10 §2.2） |
|---|---|---|
| 编制中 | `waiting` 等待版 | `-waiting` |
| 待确认稿 | `waiting` 等待版 | `-waiting` |
| 退回修订 | `review` 复核版 | `-review` |
| 已确认提交版 | `final` 完成版 | `-final` |
| 被新版替代 | `terminated` 终止版 | `-terminated` |

> **口径唯一**：文件名后缀以 #10《输出格式规格》§2.2 为准（`-waiting` / `-review` / `-final` / `-terminated`，连字符前缀）。本票早期草稿里的 `_wait` / `_review` / `_final` / `_terminated` 作废。
> 「被新版替代」是**版本关系**不是第五个成果态：D 组枚举仍为四值，旧文件的处理见 #10 §2.4（索引行置 `superseded_by`）。

旧成果不得被静默覆盖：被新版替代的旧文件保留在成果目录，状态改为被新版替代，指向取代它的新文件。

### 2.3 节点内不跳项不并行

- 节点内的子步骤**必须串行**：前一步未产出「已具交接条件」，后一步不得启动。
- 节点**之间**允许并行，但并行必须落在不同路径或不同节点，且合拢时不得互相覆盖同一产物（产物命名含节点编号，见 #10）。
- 同一节点不得开两个并发实例（避免同一锚点表被两份判定覆盖）。

| 路径 | 节点序列 | 触发条件 |

### 3.3 路径的进入与退出条件

- 进入：路径由审核员显式选择并记录选择理由；系统不得自动把任务归入 P1。
- 退出：路径走到末节点并产出汇总后，任务维转已完成。
- 中途改路径：只允许向前推进到更后面的路径（如 P2 → P1），不允许回退；回退需求走 §6.3 的退回机制。
- 一条任务只走一条路径；多标准不产生多条路径（多标准的处理见 §7）。

## §4 节点状态机

### 4.1 状态集合

节点状态（11 态）：待执行、进行中、等待补件、整改中、等待现场核实、等待人员确认、等待机构结果、已具交接条件、已完成、不适用、终止。

11 态中属阻塞的共 5 类：「等待补件」「整改中」「等待现场核实」「等待人员确认」「等待机构结果」。其中带「等待」前缀的 4 态差别在于等谁——等材料（补件）、等人到现场、等人确认、等机构给结果；另加「整改中」1 态。等待对象不同，补件方式与恢复路径不同，任何两类都不得合并成一个「等待中」。

### 4.2 合法迁移表

| 当前态 | 允许迁移到 | 迁移触发（必须留痕） |
|---|---|---|
| 待执行 | 进行中 / 不适用 | 节点启动，或经理由确认本节点对本任务不适用 |
| 进行中 | 等待补件 / 整改中 / 等待现场核实 / 等待人员确认 / 等待机构结果 / 已具交接条件 / 终止 | 缺件 / 发现整改项 / 需现场核实 / 需人工确认 / 需外部结果 / 检查项全通过 / 触发终止情形 |
| 等待补件 | 进行中 / 终止 | 补充材料到位并登记版本，按原接受条件复核 |
| 整改中 | 进行中 / 终止 | 整改证据到位并登记版本 |
| 等待现场核实 | 进行中 / 终止 | 现场核实完成并留存记录 |
| 等待人员确认 | 进行中 / 终止 | 人工确认落名 |
| 等待机构结果 | 进行中 / 终止 | 外部结果取得并记录来源 |
| 已具交接条件 | 已完成 | 交接确认 |
| 已完成 | 无（终态） | — |
| 不适用 | 无（终态，须有理由与确认人） | — |
| 终止 | 无（终态，须有终止理由） | — |

### 4.3 禁止迁移（工具须拒绝）

| 禁止 | 原因 |
|---|---|
| 进行中 → 已完成 或 已具交接条件（跳过检查项） | 状态机可被工具强制（票面验收） |
| 任何等待态 → 已完成 | 未复核不得交接 |
| 待执行 → 已完成 | 节点未启动 |
| 已完成 → 进行中 | 同一节点重开必须新开节点实例并保留旧实例 |
| 任意态 → 直接产生符合或不符合结论（未经锚点表） | 不得跳过锚点表直接出结论（票面验收） |
| 任意态 → 改标不适用而未先有依据与理由确认 | 不得把未提供改标为不适用 |
| 辅助判断 pending → conform 或 nonconform 直达 | pending 只能先落 insufficient |
| 同一节点两个并发实例 | 同一锚点表被两份判定覆盖 |

### 4.4 任务级状态机

| 任务态 | 含义 | 与节点态的关系 |
|---|---|---|
| 进行中 | 至少一个节点处于进行中或等待态 | — |
| 暂停 | 审核员主动挂起 | 当前节点可停在进行中或等待态 |
| 等待必要输入 | 全部在办节点均处于等待补件或等待机构结果 | 不得用暂停掩盖缺件 |
| 已完成 | 末节点完成且汇总产出 | 全部节点为已完成或不适用 |
| 已终止 | 触发终止情形 | 相关节点转终止；已产成果转终止版 |

「等待必要输入」与「暂停」必须分开：前者是缺件被动卡住（要向委托人要东西），后者是人主动挂起（不欠材料）。混用会让催办清单失真。

## §5 交接规则

### 5.1 交接三件套

任何节点向下一个节点（或向人）交接时，必须同时给出三件东西，缺一不得交接：

1. **产物**：该节点按 #10 约定的固定文件名的成果文件（含文件级四态后缀）。
2. **机器可读契约摘要**：该节点 contract.json（#18 产出）的关键字段快照，含规则编号、来源 sha256、状态。
3. **未决事项清单**：缺件、冲突、待人工确认项、待核数值项，逐条带责任人与期望回复。

### 5.2 双成果

| 接收物 | 用途 | 内容要求 |
|---|---|---|
| 正式文件（formal） | 进入成果目录，作为留痕与交接依据 | 完整、可归档、编号稳定 |
| 简报（brief） | 沟通交接用 | 一页以内，指明结论、缺口、下一步与责任人 |

正式文件进成果目录，简报不代替正式文件；两者不得互相矛盾（简报必须由正式文件生成，不得手写另一套结论）。

### 5.3 交接前置条件（机器可判定）

节点转「已具交接条件」前，以下全部为真才允许：

- 本节点《成果与完成交接规范》的逐项完成检查表全部为已执行，且有通过证据；
- 本节点所有规则均已判定，不存在未判定的检查项；
- 不存在未结的等待态（等待补件、整改中、等待现场核实、等待人员确认、等待机构结果）；这些可作为已登记的未决事项随交接传下去，但必须显式列出，不得隐藏；
- 若本节点产出判定，则锚点表已存在，且每个结论可回指锚点与依据（依据核验为 unverifiable 时不得出终值，只能落证据不足）；
- 数值类结论（人日、时间、比例、期限）均引自 #21 的计算结果，且 source_ref 与核验状态齐备。

### 5.4 交接记录字段

每次交接写一条不可变记录：

| 字段 | 说明 |
|---|---|
| handoff_id | 交接编号 |
| task_id / node_id | 任务与节点 |
| from_state / to_state | 迁移前后状态 |
| artifacts | 产物清单（文件名 + sha256 + 四态） |
| contract_digest | 契约摘要指纹 |
| open_items | 未决事项清单 |
| numeric_refs | 引用的数值计算记录 |
| actor / confirmed_by | 操作人与确认人 |
| timestamp | 时间 |

交接记录只追加不修改；被推翻的交接以新记录追加，旧记录保留。

## §6 阻塞、补件与恢复

### 6.1 缺件即停

- 任一必需检查缺件、冲突、未核验或缺必要确认，节点立即停在该检查点，转入对应等待态，产出双成果并标注未完成、等待处理。
- 停下来的节点不得进入下一项，也不得与本节点内其他检查并行推进（节点内不并行）。
- 缺件不直接证明企业未实施：缺件对应的判定只能是证据不足，问题分类为缺件（missing）。

### 6.2 补充材料后复核

补充材料到达后：

1. 登记新材料版本（原文件名、路径、sha256、取得时间、来源人）；
2. 在**当前项**按原接受条件复核，不重新定义接受条件；
3. 不得因补充材料而改标不适用；
4. 复核结论写明它改变了哪一条判定、依据哪条锚点；
5. 补充材料未解决原缺口时，保持原状态。

### 6.3 退回与回退点

前项有错需要回退时，必须记录：

| 字段 | 说明 |
|---|---|
| rollback_from | 出错节点 |
| rollback_to | 回退到哪个节点 |
| reason | 错误描述 |
| evidence | 证明出错的锚点与依据 |
| affected_downstream | 受影响的下游节点与已出成果 |
| disposition | 受影响成果的处理（作废、标被新版替代、重出） |

下游已确认的成果不得静默改写：只能作废重出或标被新版替代，并保留旧版本。

### 6.4 恢复后的状态回写

恢复后节点回到进行中直至检查项全通过；只有再次满足 §5.3 全部前置条件，才可再次转已具交接条件。每次恢复写一条恢复记录（补件批次号、复核人、复核结论）。

## §7 标准集合、标准版本与数值依赖

### 7.1 标准集合的选择模型

一次审核任务携带的**标准集合**由三部分决定，全部可从库文件读出，不允许由模型临时判断：

| 组成 | 取值来源 | 落点 |
|---|---|---|
| 体系画像 | `audit-point-library/registry.yaml` 的 `profiles[]`（`qms-gbt19001-2016` / `ems-gbt24001-2016` / `ohs-gbt45001-2020`） | 决定加载哪几棵条款树、哪些审核点 |
| 条款树 | `audit-point-library/clause_trees/*.yaml` | 决定「本标准有哪些条款」的唯一事实源 |
| 条款版本与过渡状态 | 同画像的 `iso_side_status` 段（数据源 `docs/research/standard-version-watch.md`） | 决定用哪个版本号、是否进入换版路径 |

规则：

- **画像可多选，路径不可多选**。多标准（如 QMS+EMS）只产生一条任务路径（P1～P7），在节点内并行审核多套标准，判定记录按 `profile_id` 分开落盘。
- **条款树不匹配即停**。任务声明的体系在 `registry.yaml` 中没有对应画像，或画像的 `clause_tree_ref` 指向的文件不存在 → 节点直接进入「等待补件」，不得以「按记忆的标准」继续。
- **版本号随条款树走**。判定记录、审查表、报告里出现的标准号必须取自条款树的 `standard` 字段（如 `GB/T 19001-2016`），不得由模型书写。
- **换版期双轨**。当 `iso_side_status.iso_withdrawn_on` 非空而国标仍现行时，任务锁定国标版本，同时在 §7.4 的换版差异台账中记录 ISO 侧状态，供 N16 使用。

### 7.2 数值依赖（本票不写死任何数值）

本规格**不含任何**人日、抽样比例、时限、间隔天数等数值。这些数值只有一个来源：#21 的计算模块。

| 数值类别 | 计算入口 | 参数来源 | 口径 |
|---|---|---|---|
| 审核人日 | `tools/calculate.py`（人日域） | `tools/params.yaml`（CNCA 附录 B 区间 + 风险系数） | 每算保留 输入 / 单位 / 口径 / 公式 / 舍入 / 复算 六项 |
| 现场占比与间隔 | `tools/calculate.py` + `tools/calendar_ratio.py`（日历域） | 同上 | 两阶段间隔、现场占比按 CNCA 规则计算 |
| 抽样数量 | `tools/calculate.py`（抽样域） | 同上 | 总体 / 样本选择方法 / 覆盖限制 / 风险依据 / 已选 / 已排除 六字段 |
| 严重不符合验证时限 | `tools/params.yaml`（时限域） | CNCA 规则 | 与 QMS / EMS / OHS 分体系取值 |

硬规则：

1. 本票正文出现的任何数字都必须带「引自 #21 计算结果」或「引自 #20 依据库」。没有来源的数字视为缺陷。
2. **不写死数值**指：数值由计算模块按输入参数算出，输入参数（组织规模、行业风险、场所数）由审核员填写并留痕；模型不得为凑一个「合理数字」而调整参数。
3. 计算结果落 `process.json` 的 `numeric_dependencies[]`，字段 `kind` / `input` / `unit` / `caliber` / `formula` / `rounding` / `recompute` / `source_ref` / `value`（与 #9 §6、#9 §10.3 一致）。
4. 参数缺失 → 该节点不得给出建议数值，只能给出「缺参数」的待办；不得以默认值代替。

### 7.3 抽样在流程中的位置

抽样发生在 **N09 审核策划配合** 与 **N12 第二阶段** 两处，两处的抽样是**不同对象**，不得合并：

| 位置 | 抽样对象 | 抽样依据 | 记录落在 |
|---|---|---|---|
| N09 | 审核范围、审核点、时间与场所 | 多场所组织的场所抽样、条款抽样 | 审核方案（#9 §6.1 六字段） |
| N12 | 具体过程、样本记录、访谈对象 | 现场过程抽样 | 过程底稿 `judgements[]` + 抽样记录 |

抽样合规性由 #9 §6 判定（判据：总体、样本选择方法、覆盖限制、风险依据、已选样本、已排除样本六项齐全且与范围一致）。**抽样记录缺字段 → 该条款落 `insufficient`，不得落 `conform`。**

### 7.4 标准换版差异台账

换版（P6）不重写审核点，而是产生**差异映射**：

| 差异类型 | 判定 | 动作 |
|---|---|---|
| 条款号不变、要求变严 | 沿用旧条款号 + 记录要求差异 | 换版后首次审核必查该条款 |
| 条款号不变、要求变松 | 同上 | 记录，不强制追加 |
| 条款号变化 | 走别名路由（`shared/aliases.yaml`） | 旧编号映射到新编号，映射关系随判定记录落盘 |
| 条款新增 | 新增条款号 | 进差异台账「新增」类 |
| 条款删除 | 旧条款号 | 落 `na`（不适用）并注明「该条款在本版本已删除」 |

台账是 N16 的输入，格式与 #9 §7 的依据快照字段对齐（`source_ref` / `snapshot_sha256` / `verified_at`）。**换版差异台账不得由模型凭记忆生成**，须以条款树与版本台账的机械比对产出。

### 7.5 依据依赖（指向 #20）

任何一条判定都必须能追到依据快照。依据由 #20 的依据库提供，本票只负责在状态机上**卡住依据缺失的节点**：

| 情形 | 依据库返回 | 节点动作 |
|---|---|---|
| 依据存在且 `current` | 正常 | 继续 |
| 依据 `superseded` | 退出码 2 | 等待补件，提示取新版依据 |
| 依据 `unverifiable` | 退出码 3 | 该条款只能落 `insufficient`（#9 §7.3），节点不得推进到「已具交接条件」 |
| 依据未登记 | 错误码 `BASIS_NOT_REGISTERED` | 等待补件 |

注：#20 的 `check` 只比对来源提供的**名称与标题**，不比对文件内容；同名改内容不会被发现，补偿手段是 sha256 快照比对（#20《依据库》已知局限）。因此本票要求：**凡是对外交付的成果，其依据快照必须带 sha256，且索引里的 `sha256` 与快照目录里的实体文件一致**（#10 §2.4 索引字段）。
## §8 与判定四态的节点级映射

### 8.1 编号命名空间冲突（先声明，避免下游踩坑）

本票的节点编号是 **N01～N17**（流程节点，流程侧）；《判定规格》§9 的 **N1～N6** 是**审核类型**（类型侧）。两套编号形似而语义不同，**不是同一套东西**。

| 命名空间 | 编号 | 语义 | 本票位置 |
|---|---|---|---|
| 流程节点 | N01～N17 | 审核流程走到哪一步 | 本票 §2 |
| 审核类型 | N1～N6 | 这一次审核属于哪一类（资格/一阶段/二阶段/监督/再认证/特殊） | 《判定规格》§9 |

**硬规则**：

- 本票正文一律用三位编号 `N12` 指流程节点；引用《判定规格》的类型时写成 `类型N2`（带「类型」前缀）或直接写「第二阶段」。
- #18 产出 `docs/spec/node-specs/<节点编号>-<名称>/` 时，目录名用三位编号；节点三件套正文里引用审核类型须写 `类型N1`～`类型N6`。
- 若发现任何一份下游文件把 `N1`～`N6` 当流程节点使用，一律按缺陷处理（登记到 §12 验收线 V-N1）。

### 8.2 流程节点 ↔ 审核类型 ↔ 判定粒度

| 流程节点 | 典型审核类型 | 允许的判定粒度（引《判定规格》§9） | 强制证据 | 禁止出现 |
|---|---|---|---|---|
| N07 申请资格检查 | 类型N1 资格审核 | 仅「是否具备接受现场审核的条件」 | 体系文件与实际活动相吻合的证明；内审与管理评审已实施的证据 | 对过程有效性下符合性判定 |
| N10 第一阶段审核配合 | 类型N2 第一阶段 | 文件层面可判定；过程有效性**不下结论** | 文件与现场一致、体系运行时间、内审与管理评审有效性、范围与重要审核点识别 | 「运行有效」「持续满足要求」类结论 |
| N12 第二阶段审核配合 | 类型N3 第二阶段 | 全量条款判定，含有效性与符合性 | 关键过程实际控制证据、绩效监视与目标达成记录 | 以一阶段文件结论代替现场证据 |
| N15 持续运行和监督 | 类型N4 监督 | 全量条款判定，重点覆盖上次结论与变化 | 上次不符合项整改验证、体系重大变更、绩效趋势 | 免于核验历史不符合项 |
| N16 再认证及标准换版 | 类型N5 再认证 | 全量条款判定 | 全周期符合性证据、有效性与持续改进 | 仅抽样复核上次结论 |
| N17 异常与特殊业务 | 类型N6 特殊 | 只对本次范围下结论 | 与投诉/扩范围事项直接相关的证据 | 顺带给出全体系符合性结论 |
| N01～N06、N09、N11、N13、N14 | 无独立类型 | 不出条款判定（只出准备度/就绪度判断） | 各自节点的交付物 | 任何条款级 conform / nonconform |

### 8.3 辅助判断（C 组）落节点规则

《判定规格》§1 定义 C 组（辅助判断 = A 四态 ∪ pending），是**人在流程中间态给的暂定结论**。它落节点的位置固定如下：

| 节点 | C 组取值 | 谁给 | 转 A 组的时机 |
|---|---|---|---|
| N03 差距分析及材料清单 | pending | 工具（默认） | 材料到位后由审核员给 insufficient 或 na |
| N07 申请资格检查 | pending → insufficient / na | 审核员 | 资格结论作出时 |
| N10 第一阶段 | pending / insufficient | 审核组 | 二阶段开始前 |
| N12 第二阶段 | A 四态全值 | 审核组 | 现场判定完成 |
| N13 不符合整改与验证 | pending | 审核组 | 验证完成后 |
| N14 认证决定和证书登记 | pending | 认证决定人员 | 本节点不出 A 组判定 |

**禁止两套口径并存**：节点表里的「结论」「状态」「判定」三列必须引用 A 组枚举原文（conform / nonconform / insufficient / na），不得写「合格」「不合格」「基本符合」等自由词。工具输出与人工输入同受此约束（#9 §1 强制条）。

### 8.4 判定四态 ↔ 节点状态机的联动

判定是**节点内**的产物，节点状态是**流程侧**的状态，两者不是一回事，但存在三条确定的联动：

| 联动 | 规则 |
|---|---|
| 判定 → 节点 | 节点内所有必检条款都已有终值判定，且不含 pending 项 → 节点方可转「已具交接条件」 |
| 节点 → 判定 | 节点处于「等待补件 / 整改中 / 等待现场核实 / 等待人员确认」时，**不得**对未满足前置的条款出终值判定；此时 C 组只能是 pending |
| 闸口 → 节点 | G1～G3 任一未放行 → 节点停在「进行中」，不得转「已具交接条件」（《判定规格》§12.3） |

### 8.5 事实标记四态（B 组）在节点上的用法

B 组（user_stated / material_supported / verified / conflict）描述**单个事实的证据强度**，与 A 组正交。落点规则：

| 节点 | 允许的最高 B 组状态 | 理由 |
|---|---|---|
| N03、N07、N09 | material_supported | 文件与策划阶段未见现场，材料支持已是上限 |
| N10 第一阶段 | material_supported（现场比对项可到 verified） | 一阶段含现场比对，但过程有效性不下结论 |
| N12 第二阶段 | verified | 现场核实后方可核验 |
| N13 整改验证 | verified | 整改证据须实际核验 |

**未确认即不足**：任何 fact_state 未到 verified 的事实所支撑的条款，不得判 conform（#9 §3.1 前置条件）。

### 8.6 节点级判定记录

每个节点在 过程底稿.json 的 judgements[] 中留下记录，字段与《判定规格》§3.4 一致；节点还须落一条**节点级就绪记录**：

```yaml
node_readiness:
  node_id: N12
  profile_ids: [qms-gbt19001-2016]
  mandatory_clauses_total: 28
  judgements_done: 28
  pending_count: 0
  insufficient_count: 3
  nc_count: 2
  gates_passed: [G1, G2, G3]
  gates_open: [G4]
  ready_to_handover: false
  blocked_reason: G4 分级闸口未放行
  numeric_dependencies: []
  basis_snapshots: []
```

硬规则：ready_to_handover 只有在**所有必检条款出终值 + 无 pending + G1～G3 已放行 + 本节点全部交付物已落盘**时才能为 true；insufficient 与 nc 本身**不阻止**交接（它们是有效结论），但 insufficient 未取得补件且已超期时要转 §6 的阻塞流程。
## §9 与成果格式的节点级对齐

### 9.1 节点 ↔ 产物矩阵

本票只规定「哪个节点产出哪些文件」；列定义、命名、占位符、版式一律以 #10《输出格式规格》为准，本节不复制其内容。

硬规则：

1. **底稿是唯一事实源**。审查表、对照表、报告、简报里的每一行/每句都必须能在 过程底稿.json 找到来源字段；禁止先写报告再补锚点（#10 §3 投影关系）。

4. **原件只读**。00_原始材料/ 下任何文件不被工具改写；派生稿不回写原件目录（#10 §2.3）。
5. 报告在 N10/N15/N16/N17 节点走**分支章节**（第一阶段报告 / 监督报告 / 再认证报告 / 特殊审核报告），分支差异由 #9 §9 的判定粒度约束，不由模板自由增删（#10 §11.1 表单族 9、10）。

### 9.2 成果状态与节点状态的对齐

### 9.3 交接即文件

节点交接不是口头确认，是**文件交接**：交接包 = 该节点的五件成果 + 节点级就绪记录（§8.6）+ 未闭环项清单。交接包落盘前，节点状态不得转「已具交接条件」。

## §10 照片取证在流程中的位置

### 10.1 照片是证据的一种载体，不是判定的替代

照片进入锚点时占《判定规格》§2 的「观察事实」要素，锚点 `anchor_id` 形如 `A-0007`，`image_region_kinds` 指明取景对象（设备铭牌、现场布局、作业状态、标识张贴等）。**照片本身不构成 `verified`**：照片的 fact_state 上限是 material_supported，除非由现场审核员本人确认后方可升为 verified（#11 承担照片取证链路）。

### 10.2 照片在节点上的分布

| 节点 | 照片作用 | 强制场景 |
|---|---|---|
| N03 差距分析 | 标注差距位置（可选） | — |
| N09 审核策划 | 场所抽样前的场所清单佐证 | 多场所组织 |
| N10 第一阶段 | 文件与现场一致的现场比对 | 必审 5 项之一（#9 类型N2） |
| N12 第二阶段 | 现场核查证据的主载体 | 现场审核检查表类条款 |
| N13 整改验证 | 整改后状态的对照照片 | 需现场复核的整改项 |
| N16 换版 | 影响面分析的现场佐证 | 换版影响的过程 |

### 10.3 不可由照片取证的事项（硬边界）

下列事项**不得**以照片作为充分证据，缺失即落 insufficient：

1. **文件内容完整性**（受控版本、审批记录、修订痕迹）——照片只能证明「桌上有这份文件」，不能证明「这份是受控版本」。
2. **访谈**（人员理解、认知、授权）——照片只能证明「有人在说」，不能证明「说的人懂且有权」。
3. **时间序列类**（10.2 纠正措施的有效性、9.3 管理评审的有效性）——照片无时序，不能证明「持续有效」。
4. **数据真实性与完整性**（记录是否真实反映实际过程）——照片不能证明记录未被补填。

### 10.4 照片取证的待办化

照片取证由 #11 承担实现。本票只规定流程侧的三件事：

- **可取证条款白名单**：由审核点库 `photo_evidence` 字段给出（shared/rules.yaml 的 photo_evidence_levels 三档：allowed / conditional / not_applicable）。只有 allowed 与 conditional 的条款才允许登记照片型锚点。
- **不可取证条款的替代路径**：not_applicable 的条款必须走书面证据或访谈记录，不得以「现场没拍到」结束。
- **modlens 视觉桥未通时的降级**：若照片内容无法自动识别，照片锚点的 fact_state 一律不高于 user_stated，并生成一条 E 组 pending_check 待办，指向审核员人工识读。
